# FASE C3 — PROCESO COMERCIAL, CONTRATACIÓN Y ACTIVACIÓN

## 1. Objetivo

Definir el proceso completo mediante el cual PQRS Services:

1. recibe un prospecto;
2. determina si es un cliente adecuado;
3. calcula su tarifa;
4. realiza el diagnóstico;
5. presenta la solución;
6. envía una propuesta;
7. gestiona descuentos y excepciones;
8. formaliza el piloto;
9. registra el pago;
10. crea el conjunto;
11. configura categorías y workflows;
12. importa residentes;
13. capacita al administrador;
14. inicia el piloto;
15. acompaña la operación;
16. convierte el piloto en una suscripción.

Este proceso está diseñado para los primeros tres pilotos y para una operación administrada inicialmente por una sola persona.

# 3. Estados del proceso comercial

Todo prospecto debe tener un único estado vigente.

```text
NUEVO
→ CONTACTADO
→ DIAGNÓSTICO AGENDADO
→ CALIFICADO
→ DEMOSTRACIÓN REALIZADA
→ PROPUESTA ENVIADA
→ EN DECISIÓN
→ PILOTO ACEPTADO
→ PENDIENTE DE INFORMACIÓN
→ PENDIENTE DE PAGO
→ PAGADO
→ EN IMPLEMENTACIÓN
→ LISTO PARA LANZAMIENTO
→ PILOTO ACTIVO
→ EVALUACIÓN FINAL
→ CONVERTIDO
```

Estados alternativos:

```text
NO CALIFICADO
SIN RESPUESTA
POSPUESTO
PROPUESTA RECHAZADA
PILOTO CANCELADO
NO CONVERTIDO
```

No se debe marcar un cliente como ganado únicamente porque aceptó una reunión o recibió una propuesta.

Un cliente se considera comercialmente ganado cuando:

* pagó el piloto; o
* firmó la aceptación y existe una fecha de pago definida.

# 5. Primer contacto

El objetivo del primer contacto no es vender inmediatamente.

El objetivo es conseguir una conversación de diagnóstico de aproximadamente 20 minutos.

## Mensaje inicial

La comunicación debe enfocarse en el problema:

> Ayudamos a administraciones de conjuntos residenciales a centralizar las solicitudes de los residentes, controlar responsables y tiempos, y demostrar la gestión ante el consejo mediante historial y evidencia.

No presentar inicialmente:

* arquitectura;
* multi-tenancy;
* tecnologías;
* inteligencia artificial;
* Reservas;
* Pagos;
* veinte funciones;
* terminología técnica.

## Resultado esperado

Uno de estos cuatro resultados:

1. diagnóstico agendado;
2. no tiene el problema;
3. no es la persona que decide;
4. no es prioridad actualmente.

Cuando no sea la persona decisora, solicitar:

* nombre;
* cargo;
* correo;
* forma de introducción.

# 6. Diagnóstico comercial de 20 minutos

La reunión debe validar dolor, urgencia, autoridad y capacidad de implementación.

## Bloque 1 — Operación actual

Preguntar:

1. ¿Por qué canales reciben actualmente las solicitudes?
2. ¿Cuántas reciben aproximadamente cada mes?
3. ¿Quién las recibe?
4. ¿Cómo asignan responsables?
5. ¿Dónde queda registrado el seguimiento?
6. ¿Cómo se sabe cuáles siguen pendientes?
7. ¿Cómo se informa al consejo?
8. ¿Qué ocurre cuando cambia el administrador o un empleado?

## Bloque 2 — Problemas

Preguntar:

1. ¿Se han perdido solicitudes?
2. ¿Los residentes reclaman que no se les respondió?
3. ¿Es difícil reconstruir el historial?
4. ¿Cuánto tiempo toma preparar informes?
5. ¿Hay varios responsables o proveedores?
6. ¿El consejo pide evidencia?
7. ¿Continúan procesos importantes por WhatsApp personal?
8. ¿Qué parte les genera más desgaste?

## Bloque 3 — Decisión

Preguntar:

1. ¿Quién aprueba la contratación?
2. ¿Debe aprobarlo el consejo?
3. ¿Existe presupuesto para herramientas administrativas?
4. ¿Cómo pagan normalmente a sus proveedores?
5. ¿Requieren cuenta de cobro o factura?
6. ¿Cuándo podrían iniciar?
7. ¿Qué tendría que demostrar un piloto para continuar?

## Bloque 4 — Implementación

Preguntar:

1. ¿Cuántas unidades tiene el conjunto?
2. ¿Cuántos administradores o responsables usarían el sistema?
3. ¿Tienen una base organizada de residentes?
4. ¿Quién se encargaría de liderar la implementación?
5. ¿Pueden canalizar casos reales por la plataforma?
6. ¿El consejo participaría en la evaluación final?

# 7. Calificación del prospecto

## Prospecto calificado

Debe cumplir preferiblemente:

* entre 150 y 500 unidades;
* diez o más solicitudes mensuales;
* uso de varios canales;
* dificultad de seguimiento;
* consejo activo;
* administrador comprometido;
* fecha posible de inicio;
* capacidad de realizar un piloto pago;
* disposición para usar casos reales.

## Prospecto parcialmente calificado

Puede continuar cuando:

* tiene menos solicitudes, pero un problema importante;
* administra varios conjuntos;
* tiene menos de 150 unidades, pero alta complejidad;
* desea empezar con un solo conjunto antes de expandirse.

## Prospecto no calificado

No se prioriza cuando:

* solo quiere una página informativa;
* exige desarrollo personalizado antes de pagar;
* no acepta usar casos reales;
* espera soporte operativo a todos los residentes;
* exige WhatsApp, contabilidad o portería como requisito;
* no existe una persona responsable de implementar;
* no puede tomar una decisión en un plazo razonable;
* pretende un piloto gratuito indefinido;
* no tiene presupuesto ni autoridad.

## Regla

No hacer demostraciones largas a prospectos no calificados.

# 8. Cálculo de tarifa

## Variable principal

La tarifa se calcula por el número de unidades privadas registrado por el conjunto.

```text
1–100 unidades      → $119.000 mensuales
101–200 unidades    → $159.000 mensuales
201–400 unidades    → $199.000 mensuales
401–600 unidades    → $249.000 mensuales
Más de 600          → cotización individual
```

## Información requerida

Antes de cotizar:

* número exacto de unidades privadas;
* si existe uso mixto residencial/comercial;
* cantidad de conjuntos que maneja el administrador;
* si solicita piloto;
* modalidad mensual o anual;
* si es cliente fundador;
* si existe referido;
* complejidad de implementación;
* módulos adicionales solicitados.

## Unidades comerciales o mixtas

Cuando el conjunto tenga apartamentos, locales u otras unidades privadas:

* todas las unidades privadas administradas se suman;
* parqueaderos y depósitos no cuentan como unidades independientes cuando pertenecen a una unidad principal;
* locales independientes sí cuentan;
* cualquier excepción debe documentarse.

## Más de 600 unidades

La cotización individual debe considerar:

* número de unidades;
* volumen estimado de PQRS;
* cantidad de administradores;
* almacenamiento;
* implementación;
* soporte;
* módulos solicitados;
* proceso contractual.

No aplicar automáticamente una tarifa proporcional.

---

# 9. Regla de precio único

Para los primeros pilotos:

* el mismo núcleo de Gestión se ofrece a todos;
* no se cobran usuarios adicionales;
* no se cobra por número de PQRS;
* no se cobran administradores adicionales;
* no se crean restricciones técnicas por plan;
* no se reduce el alcance central para abaratar.

La diferencia de precio depende principalmente del tamaño del conjunto.

La actividad y el soporte se medirán para revisar esta política posteriormente.

# 13. Descuentos

## Descuento anual

* 10 %;
* pago anticipado;
* no acumulable;
* no aplicable al piloto.

## Descuento comercial

* máximo 5 %;
* únicamente autorizado por el fundador;
* debe tener motivo;
* debe tener fecha de finalización;
* no acumulable con anualidad;
* no aplicable al piloto.

## Casos válidos

* cierre de negociación sensible al presupuesto;
* incorporación de varios conjuntos;
* cliente estratégico;
* compromiso contractual específico.

## Casos no válidos

* el cliente lo pidió sin justificación;
* el referido lo prometió;
* evitar explicar el valor;
* igualar automáticamente a cualquier competidor;
* compensar funcionalidades que no forman parte de la oferta.

# 14. Clientes fundadores

Los primeros diez clientes que paguen y continúen reciben:

* implementación asistida sin costo;
* precio protegido durante doce meses;
* acompañamiento inicial;
* prioridad para entrevistas de producto.

## Precio protegido

Significa que:

* conservan la tarifa base contratada durante doce meses;
* el beneficio no se transfiere;
* add-ons se cotizan aparte;
* impuestos o costos externos pueden tratarse separadamente;
* el precio puede cambiar después del periodo protegido mediante aviso previo.

No significa descuento permanente.

---

# 15. Referidos y comisión

## Registro obligatorio

Antes de enviar la propuesta debe registrarse:

* nombre del referido;
* fecha;
* prospecto referido;
* relación;
* acuerdo aplicable.

## Política general

La comisión será equivalente a una mensualidad neta.

Se paga cuando:

* el piloto convierte;
* el cliente completa su segundo pago mensual;
* no existen devoluciones o disputas.

## Base de cálculo

Se calcula sobre:

* valor efectivamente recibido;
* después de descuentos;
* después de devoluciones;
* después de impuestos cuando aplique;
* después de costos directos de pasarela, si así se define contractualmente.

## No genera comisión

* piloto no convertido;
* cortesía;
* cliente previamente existente;
* contacto sin participación real;
* cliente moroso;
* reactivación de cliente antiguo;
* add-ons futuros, salvo acuerdo distinto.

## Excepción fundadora

El acuerdo con la administradora inicial puede reconocer el valor del primer mes como comisión especial.

Debe documentarse como excepción y no convertirse automáticamente en la política general.

# 16. Formas de pago

## Piloto

Preferencia inicial:

1. transferencia bancaria;
2. pago manual registrado;
3. Mercado Pago cuando resulte conveniente.

El piloto debe pagarse antes de iniciar la implementación.

## Mensualidad

Opciones:

* transferencia anticipada;
* Mercado Pago recurrente;
* pago manual confirmado por SUPER_ADMIN.

## Anualidad

* pago anticipado por transferencia;
* activación por doce meses;
* registro manual auditado;
* no requiere automatización adicional durante los primeros clientes.

## Regla

No activar el conjunto únicamente con un comprobante enviado.

Debe verificarse:

* recepción efectiva;
* referencia;
* pagador;
* valor;
* concepto;
* fecha.

# 19. Validación de la información

Antes de importar:

* confirmar cantidad de filas;
* eliminar duplicados evidentes;
* validar formato de correos;
* detectar apartamentos repetidos;
* identificar campos faltantes;
* confirmar que la base fue entregada por una persona autorizada;
* registrar fecha y versión del archivo.

PQRS Services no asume limpieza ilimitada.

Cuando la plantilla esté incompleta:

1. se devuelve con errores;
2. el cliente corrige;
3. se fija nueva fecha;
4. no se retrasa indefinidamente el cronograma por trabajo gratuito.

# 20. Pago y creación del conjunto

## Secuencia obligatoria

```text
Propuesta aceptada
→ documentos recibidos
→ pago confirmado
→ creación del tenant
→ administrador principal
→ configuración
→ importación
→ prueba
→ capacitación

```

No crear tenants definitivos para prospectos que únicamente solicitan una demostración.

## Datos que determinan la tarifa

Al crear el conjunto se registra:

* número de unidades;
* rango comercial;
* precio mensual;
* valor del piloto;
* beneficio fundador;
* descuento;
* referido;
* modalidad de pago;
* fecha de inicio;
* fecha de finalización del piloto;
* precio posterior.

Aunque inicialmente parte de esta información se gestione manualmente, debe existir una ficha comercial única.

# 21. Configuración inicial

## Categorías

Se configura únicamente lo necesario para el piloto.

Cada categoría debe tener:

* nombre;
* estado;
* orden;
* workflow;
* justificación operativa.

No crear categorías específicas por cada situación aislada.

## Workflow SIMPLE

Para:

* convivencia;
* certificados;
* consultas;
* correspondencia;
* asuntos administrativos;
* solicitudes que no requieren proveedor.

## Workflow MAINTENANCE

Para:

* reparaciones;
* daños;
* inspecciones;
* adquisición de insumos;
* contratación de proveedor;
* ejecución física.

## Categorías personalizadas

Máximo tres.

Solo se crean cuando:

* existe un proceso recurrente;
* no encaja razonablemente en las ocho categorías;
* el administrador confirma que será utilizado.

# 22. Importación de residentes

## Responsabilidad del cliente

Debe entregar:

* plantilla completa;
* información autorizada;
* correos válidos;
* unidades correctamente identificadas.

## Responsabilidad de PQRS Services

* validar estructura;
* importar;
* informar errores;
* proteger la información;
* no usar los datos para finalidades distintas;
* eliminar copias temporales según la política acordada.

## Criterio de aceptación

La carga queda aceptada cuando:

* totales coinciden;
* muestras fueron verificadas;
* administrador confirma;
* no existen errores críticos;
* invitaciones pueden enviarse.

# 24. Pruebas antes del lanzamiento

Antes de invitar masivamente:

1. ADMIN ingresa;
2. RESIDENTE de prueba ingresa;
3. se crea una PQRS;
4. se adjunta evidencia;

# 25. Lanzamiento

## Día de lanzamiento

* activar acceso;
* enviar invitaciones;
* compartir comunicación preparada;
* confirmar al administrador;
* crear una primera PQRS real acompañada;
* verificar correos;
* registrar incidentes;
* confirmar el inicio de los 30 días de uso efectivo.

## Regla de inicio del piloto

Los 45 días incluyen hasta siete días de preparación.

Los treinta días de uso real empiezan cuando:

* la carga está aceptada;
* el administrador está capacitado;
* las invitaciones principales fueron enviadas;
* puede crearse una PQRS real.

---

# 26. Soporte durante el piloto

## Canal

* correo de soporte;
* tickets del sistema;
* reunión semanal programada.

No usar WhatsApp personal como canal permanente.

## Usuarios atendidos directamente

* administrador;
* responsable autorizado.

Los residentes solo reciben soporte directo para:

* acceso;
* fallas técnicas;
* privacidad o seguridad.

Los asuntos operativos se remiten a la administración.

## Alcance incluido

* errores de plataforma;
* dudas de uso;
* acompañamiento razonable;
* revisión semanal;
* corrección de configuración inicial.

## No incluido

* operación diaria del conjunto;
* responder PQRS;
* perseguir proveedores;
* limpiar bases continuamente;
* capacitaciones ilimitadas;
* personalizaciones;
* soporte jurídico;
* soporte financiero de residentes.

---

# 27. Seguimiento semanal

Cada revisión debe durar aproximadamente 20–30 minutos.

## Revisar

* PQRS creadas;
* porcentaje gestionado en plataforma;
* casos que siguieron por WhatsApp;
* tiempos;
* errores de clasificación;
* correcciones;
* soporte;
* percepción del administrador;
* participación del consejo;
* bloqueantes.

## Registrar

* fecha;
* participantes;
* métricas;
* decisiones;
* tareas;
* responsable;
* fecha de cumplimiento.

No desarrollar una funcionalidad por una sola solicitud.

---

# 28. Evaluación final

La reunión final debe estar agendada desde antes de iniciar.

## Participantes

* administrador;
* persona decisora;
* representante del consejo;
* PQRS Services.

## Presentar

* número de casos;
* adopción;
* tiempos;
* historial;
* uso de evidencias;
* solicitudes fuera de plataforma;
* tiempo ahorrado;
* soporte requerido;
* problemas detectados;
* recomendación.

## Decisión

Una de cuatro:

1. continuar mensual;
2. continuar anual;
3. extender excepcionalmente por causa documentada;
4. terminar y exportar.

No permitir extensiones indefinidas sin pago.

---

# 29. Conversión

## Continuidad mensual

* se confirma precio;
* se emite cobro;
* se registra pago;
* se activa el siguiente periodo;
* se confirma soporte y condiciones.

## Continuidad anual

* se aplica 10 %;
* se recibe pago anticipado;
* se registra periodo;
* se protege tarifa según condición fundadora.

## Sin continuidad

* se define fecha de terminación;
* se detienen renovaciones;
* se exporta información;
* se aplica política de recuperación;
* se elimina o conserva según acuerdo;
* se documenta motivo de rechazo.

---

# 30. Casos especiales

## Cliente quiere comenzar sin pagar

Respuesta:

* no se activa el piloto;
* puede realizar diagnóstico y demostración;
* se conserva el prospecto;
* no se importan datos reales.

## Cliente no entrega la base

* se mantiene pendiente;
* se fija fecha límite;
* el cronograma se desplaza;
* no se consume acompañamiento indefinido.

## Cliente quiere personalización

Clasificar:

* error del producto;
* configuración;
* necesidad común;
* solicitud particular.

Solo se desarrolla cuando:

* bloquea el piloto;
* implica riesgo;
* aparece en varios clientes;
* existe disposición a pagar.

## Cliente solicita Reservas o Pagos

* no se incluyen automáticamente;
* se realiza diagnóstico separado;
* se cotiza implementación;
* no retrasa el piloto de Gestión.

## Empresa con varios conjuntos

* se cotiza cada conjunto;
* se incorpora uno primero;
* desde el tercero puede evaluarse descuento de 10–15 %;
* no se promete dashboard consolidado.

## Cambio en número de unidades

* se actualiza en renovación;
* si cambia de rango, se informa el nuevo precio;
* no se ajusta retroactivamente.

## Mora

* se aplica periodo de gracia;
* se notifica;
* se suspende según la política;
* la información no se elimina automáticamente;
* la reactivación exige pago o autorización válida.

# 33. Reglas de decisión

## Continuar escalando

Cuando:

* al menos dos de tres pilotos convierten;
* pagan al menos 80 % del precio de lista;
* más del 70 % de nuevas PQRS entra a la plataforma;
* soporte baja de una hora mensual por conjunto;
* no existen incidentes críticos;
* no exigen módulos adicionales para continuar.

## Ajustar oferta

Cuando:

* usan el producto, pero rechazan precio;
* el administrador percibe valor y el consejo no;
* la implementación consume demasiado;
* Esencial aparece como necesidad recurrente;
* Reservas o Pagos aparecen repetidamente.

## Detener expansión

Cuando:

* menos de dos pilotos usan el sistema;
* más de la mitad de procesos sigue fuera;
* todos exigen otros módulos;
* soporte supera dos horas mensuales por conjunto;
* aparecen problemas de privacidad o aislamiento;
* nadie acepta pagar el precio posterior.

# 34. Fuente de verdad comercial

Cada prospecto debe tener una ficha única con:

* información;
* diagnóstico;
* rango;
* precio;
* descuentos;
* referido;
* propuesta;
* documentos;
* pago;
* implementación;
* métricas;
* decisión.

No deben existir precios diferentes dispersos entre WhatsApp, correos y documentos.

Toda excepción debe quedar registrada.

---

# 35. Resultado de C3

El proceso comercial oficial será:

```text
Prospecto
→ contacto
→ diagnóstico
→ calificación
→ demostración
→ tarifa
→ propuesta
→ decisión
→ documentos
→ pago
→ creación
→ configuración
→ importación
→ capacitación
→ pruebas
→ lanzamiento
→ seguimiento
→ evaluación
→ conversión o salida
```

No se debe crear código adicional para automatizar este proceso durante los primeros tres pilotos.

Primero debe ejecutarse manualmente, registrar tiempos y detectar qué actividades realmente justifican automatización.
